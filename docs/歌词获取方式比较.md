# 歌词获取方式比较

这份文档记录 Color lyric 内置歌词获取的设计，以及参考项目之间的区别。阅读源码的时间为 2026 年 11 月 26 日；下文提到的「已接入」指代码入口已接入，不代表每个播放器、每种系统版本都已经过真机验证。当前工作仍在 `codex/builtin-lyrics` 分支，最终完成情况以本文件末尾的状态为准。

## 先说结论

同一首歌的歌词可以从三个地方来：**播放器自己、播放器主动发送的接口、网上搜索**。它们不是三种不同的显示动画，而是歌词进入 Color lyric 之前的三条路。

例如正在听一首网易云歌曲：

1. **播放器直取**：从当前播放器提供的歌词或 Hook 到的歌词数据取完整时间轴，适合优先保留正在听的版本。
2. **播放器接口**：播放器主动把歌词发给实现了其约定协议的接收端。能不能用取决于双方是否实现同一套协议，并不是安装了任意歌词模块就自然兼容。
3. **网络搜索**：用歌名、歌手、专辑、时长等信息去其他曲库找相同的歌，再下载歌词。播放器不暴露歌词时也能尝试，但搜到的版本和正在播放的版本可能不同。

内置提供者有「**播放器优先**」和「**网络搜索**」两种获取方式：前者先等待播放器歌词，再按设置顺序联网兜底；后者按设置搜索网络源。提供者还可以切换为媒体会话自带的 LyricInfo，或外部 SuperLyric。格式、显示样式和获取方式是不同概念：TTML、QRC、YRC 是歌词数据格式，不是播放器或一个独立的搜索网站。

## 几种方法有什么不同

| 方式 | 怎么取得歌词 | 优点 | 局限 |
| --- | --- | --- | --- |
| 直接使用播放器写入媒体会话的 `lyricInfo` | 读取当前媒体会话已有的歌词 | 不必搜索；通常与正在播放的版本一致；能使用播放器本身的时间轴 | 不是所有播放器都会提供完整歌词、逐字时间和翻译；系统字段也可能随实现变化 |
| 针对播放器 Hook | 在播放器进程内观察它的歌词模型，再写入该播放器自己的媒体会话 | 对已适配的播放器可以保留本地或官方歌词、逐字和翻译 | 每个播放器的内部结构不同；播放器升级可能失效；需要在 LSPosed 给相关播放器作用域并重新启动播放器 |
| 播放器主动发布 API | 播放器将完整歌词发送给协议接收端 | 协议稳定时不必理解播放器内部实现 | 需要接收端实现相同协议；SuperLyric API 与 `lyricInfo`、Lyricon 是不同协议，不能混为一谈 |
| 媒体会话信息 + 网上搜索 | 观察歌曲信息，根据标题、歌手和时长匹配曲库，再下载歌词 | 适用播放器范围广；无专用 Hook 也能尝试；缓存后可复用 | 消耗网络请求；可能遇到版权、地区、接口变动或搜索不到；同名、现场版、重录版和不完整的媒体信息可能导致错配 |
| 手动搜索并绑定 | 用户搜索并选择具体结果，保存与当前歌曲的绑定 | 自动匹配错误时可以指定版本 | 需要手动操作；歌曲信息变化后匹配仍取决于绑定标识 |

直取的时间轴也不保证绝对同步：它依然取决于播放器上报的播放进度是否平稳、歌词本身是否准确，以及该版本是否确实带逐字信息。网络搜索也不是声音识别：它没有听音乐，只根据歌曲信息检索。

## 参考项目

### ColorOS Live Lyrics Bridge / Providers（上游项目）

[Bridge](https://github.com/Andrea-lyz/ColorOS-Live-Lyrics-Bridge) 侧重 ColorOS 锁屏歌词的接入和外观；[Providers](https://github.com/Andrea-lyz/ColorOS-Live-Lyrics-Providers) 则分别适配播放器，或通过通用播放器获取媒体信息并搜索歌词。二者分工不同：**Bridge 不是四个网络曲库本身**。

Providers 内的专用适配器可以把逐字和翻译追加到播放器的媒体信息；通用播放器可以按源搜索，并处理歌词格式和缓存。Color lyric 引用了 Providers 的网络接口与解析器。上游授权与署名见 `third_party/coloros-lyrics-providers/NOTICE`。

### SuperLyric

[SuperLyric](https://github.com/HChenX/SuperLyric) 把获取与发布拆开：它有针对不同播放器的 Hook 或在线兜底，再通过自己的 Binder 协议把歌词提供给客户端。其支持列表里有的播放器采用「Hook + 酷狗兜底」，有的采用网络，Flamingo、BreezyMusic 等则由播放器集成 SuperLyric API。

优点是播放器适配与客户端显示可以解耦；代价是需要对应服务和协议，不能把它的 API 声称为 ColorOS `lyricInfo` 的同义词。[BreezyMusic 的歌词发布实现](https://github.com/BlueEve04/BreezyMusic/blob/main/app/src/main/java/com/breezy/music/model/LyricPublisher.kt)会先检查 SuperLyric 接收端是否可用，然后发布整首歌；仅在支持列表中加入它的包名，并不会自动实现这个接收协议。

SuperLyric 使用 GPLv3；[SuperLyricApi](https://github.com/HChenX/SuperLyricApi) 有自己的 LGPL 授权。当前分支有两条不同的路径：内置直取时，可尝试 Hook 支持 API v4 的播放器发布调用；选择 **SuperLyric 提供者**时，则订阅已有 SuperLyric 服务，将完整时间轴、逐字和翻译转换为当前媒体会话的 `lyricInfo`。外接模式不会启动内置的自动网络搜索或播放器直取，并通过播放器包名、歌曲身份和会话代次校验，停止后只撤回本模块写入的内容。API 4 接收器支持连接旧版 3.x 服务，但只有逐行实时文本、没有完整歌词文档的旧版发布情况尚未接入。SuperLyric 外接效果及服务重连仍待 ColorOS 真机验证。

### HyperLyrics-Enhanced

[HyperLyrics-Enhanced](https://github.com/juren233/HyperLyrics-Enhanced) 不只是一个搜索器。它可以接收 Lyricon、SuperLyric 和媒体会话等不同来源，也为 Apple Music 有直连歌词桥接；其内置在线部分包括 QQ、网易云、酷我、酷狗搜索，以及按平台歌曲 ID 查询的 AMLL / LunaBeat TTML 目录。是否启用、可否命中取决于当前配置与歌曲，不能把这些 TTML 目录等同于登录后的 Apple Music 官方接口。

它值得借鉴的几处设计：

- **区分来源与歌曲身份**：在线结果要与当前歌曲重新核对，避免切歌后迟到的搜索结果覆盖新歌。
- **匹配和回退分层**：搜索时会比较歌曲信息；一些边缘匹配还会结合时长和歌词内容再判断，而不是只看歌名。
- **可选择并发或顺序**：自动来源可以同时请求，先显示可用结果，后续可升级到逐字或更高优先级的 TTML；也有按顺序选源的路径。并发通常更快，但同时发出更多请求，而且必须防止结果反复跳变。
- **缓存原始来源结果**：除了保存最终结果，还区分搜索、元数据和歌词等缓存，并避免将网络异常当作永久无词。
- **翻译补充和时间轴保留**：获取译文、逐字时间和歌曲匹配是分开处理的，逐字结果不能在转换时退化成纯逐行。

对应源码入口：[OnlineLyricTargeter](https://github.com/juren233/HyperLyrics-Enhanced/blob/main/app/src/main/java/com/juren233/hyperlyricsenhanced/online/OnlineLyricTargeter.kt)、[SearchSourceRaceSelection](https://github.com/juren233/HyperLyrics-Enhanced/blob/main/app/src/main/java/com/juren233/hyperlyricsenhanced/online/SearchSourceRaceSelection.kt)、[MediaSessionLyricsFetcher](https://github.com/juren233/HyperLyrics-Enhanced/blob/main/app/src/main/java/com/juren233/hyperlyricsenhanced/root/source/MediaSessionLyricsFetcher.kt)、[AppleMusicDirectBridge](https://github.com/juren233/HyperLyrics-Enhanced/blob/main/app/src/main/java/com/juren233/hyperlyricsenhanced/root/source/AppleMusicDirectBridge.kt)、[SuperLyricSource](https://github.com/juren233/HyperLyrics-Enhanced/blob/main/app/src/main/java/com/juren233/hyperlyricsenhanced/root/source/SuperLyricSource.kt)。这些是参考链接，不代表本项目移植了其所有实现。

HyperLyrics 的一些播放器适配还在独立的 [HLE-Providers](https://github.com/juren233/HLE-Providers) 中，而不全在主仓库里。例如波点适配使用媒体会话中的酷我曲目 ID 查询，并不是读取播放器本地歌词；小米音乐的实现同时处理应用内歌曲信息、媒体会话信息和在线 QQ 标识，源码专门说明某些版本的媒体 ID 不能直接当作在线 songmid。这个区别很重要：按 ID 网上取词可以减少搜索歧义，但仍是网络获取，也不能未经核对就把任意本地 ID 当在线曲库 ID。

## Color lyric 当前分支的设计决定

1. **保留原有流体云显示链**：歌词最终仍交给匹配到的媒体会话和原有的 ColorOS 流体云绘制，不重新实现系统岛的动画。
2. **歌词设置入口**在 COUI 悬浮底栏「设置」中，提供当前歌曲、最近歌词、搜索、缓存、播放器管理、来源和 Apple Music 设置。
3. **播放器优先，网络兜底**：当前实现对直取结果预留约 1.5 秒到达窗口，未取得有效歌词时开始网络搜索；不在每帧或每秒重复搜索。用户手动绑定的歌词优先。
4. **四个网络源**：QQ、网易云、酷狗、Apple Music；可调整顺序及启停。开启「TTML 优先」时，会优先询问可直接提供 TTML 的来源，再对合适结果转换；开启「优先使用逐字时间轴」时，较低优先级的逐字结果也可能胜过较高优先级的逐行结果。这两个选项都会影响一般来源顺序的最终结果。
5. **会话与缓存分开判断**：网络异步返回时按播放器和会话代次检查；播放器缓存标记来源，切换到网络模式时不能把播放器缓存当成网络搜索结果。手动绑定不受自动缓存有效期影响。
6. **数据保留**：自动歌词缓存使用歌曲信息索引，成功结果为 7 天、自动无词结果为 10 分钟；手动编辑保存为手动绑定。缓存命中不重新请求。切歌、歌词格式、版本匹配和持久化仍须通过设备实测。
7. **耗时和请求数**：目前采用顺序访问，单个来源最多 6 次 HTTP、约 4 秒，总计最多 24 次、约 16 秒；这是每轮搜索的上限，不是每首歌都会达到。播放器成功直取或缓存命中时通常无需网络。明确识别为网络异常的同曲目重试至少间隔 30 秒；部分来源会把异常视为未命中，这时当前曲目不一定自动重试，可切歌或调整来源后重试。手动搜索和选择下载各有独立预算；搜索结果实际可用性受网络与服务影响。没有自动的模型调用，正常、重试和回退均为 **0 次 LLM 请求**，不产生模型费用。
8. **网络范围**：允许自动取词后，歌曲元数据会发送到所选歌词源；播放器直取和缓存命中可在本地完成。Apple Music 源的官方路径需要用户登录，地区按用户选择或账户状态处理。如果官方歌词不可用，该来源还会尝试 iTunes 曲库和第三方 Better Lyrics、Paxsenix：Better Lyrics 接收歌名、歌手和时长，Paxsenix 接收曲目 ID。Apple 登录令牌只用于 Apple 官方路径，不作为这两个第三方请求的参数或请求头发送。日志不应包含歌词正文或账户令牌。

为什么当前没有直接采用 HyperLyrics 的全部并发方案：用户要求可设置来源优先级，顺序搜索更容易保证这个语义，也可以减少同时访问的服务；并发赛马有延迟优势，但会增加请求量，并需要专门处理结果替换、歌词跳变和取消。后续若实测等待过长，可以在保留来源优先级与切歌保护的前提下进一步设计，不应简单把所有来源同时请求后覆盖当前歌词。

## 当前范围与待验

- **代码入口已导入，待设备验证**：Apple Music、QQ、网易云、Salt、Cone、LX Music、Poweramp、酷狗、Spotify、汽水和酷我专用入口，以及通用媒体会话和四个网络源。是否真正生效取决于对应播放器版本、作用域、系统接口和歌词数据。
- **实验性 API 适配，待设备确认**：BreezyMusic 和声明集成 SuperLyric API v4 的播放器可以尝试按上面的发布调用路径接入；Flamingo 包名不固定，需要在播放器列表中选择并在 LSPosed 中加入对应作用域。旧版 API 与各播放器实际编译方式仍需确认。
- **仍需单独完成或确认**：波点、咪咕、酷我车机、小米的专用直取。当前不能把通用网络兜底说成这些专用入口已经完成。
- **需实机覆盖**：SuperLyric 服务重启与停止、同一播放器多会话、连续切歌和延迟返回、手动绑定／删除、禁用播放器、播放器重启、系统重启恢复、歌词格式与翻译、Apple 登录及地区和与外部歌词模块共存。Android 模拟器不能代替 ColorOS SystemUI 验证。

### 本次检查和剩余事项

- 已有本地构建、单元测试、Lint 和入口保留检查；具体结果见 `docs/acceptance.md` 的「内置歌词获取」记录。这些检查不能证明手机上的 Hook、网络源或登录流程已经可用。
